# 선물 MVP 연결 개발 명세 · v0.2.1


## v0.2.1 보완

닉네임 카드의 작은 그림은 선택한 경력에 연결한다. 입문·1년·2년·3년·4년 이상에 기존 그림 5종을 순서대로 대응시킨다. 배운 점·질문 개수는 그림 선택에 사용하지 않으며 업무 능력 평가를 의미하지 않는다.

내 대화에는 대화별 `isFavorite` 선택 필드를 추가했다. 필드가 없는 기존 기록은 미등록으로 취급한다. 별 버튼과 즐겨찾기 필터를 제공하며 로컬 저장 외의 연결은 없다.

## 이번 화면 수정 상태

v0.1의 설계와 단일 HTML 구현을 유지한 화면·흐름 수정본이다. 실제 브라우저가 로컬 HTTP·파일 열기를 차단해 PC·모바일 렌더링 검토는 미완료다. 구문, 독립된 로직 검사 14개, 생성 HTML 파싱을 확인했다. 검토 범위는 `QA_NOTES.md`를 따른다.

- 홈·채팅 입력은 열린 탭의 화면 이동 동안 보존한다. 새로고침 후 초안 복원은 없다.
- 모바일 주요 글자와 터치 영역을 키우고 채팅 상담 버튼·입력창을 재배치했다. 터치 기기 Enter는 줄바꿈, 버튼은 전송이다.
- 상담은 요약·닉네임·경력만 기본 공유한다. 추가 메시지는 직접 선택하고, 요약·선택이 바뀌면 동의를 다시 받는다.
- 상담·답변 저장 실패 시 완료로 처리하지 않는다. 외부 전송·알림은 없다.
- 성장기록은 배운 점·직접 입력된 시연 피드백·질문 이력 순서다. 횟수는 접어 두었다. 배운 점 수정·삭제를 지원한다.
- 임의 운영자 시연 답변을 제니가 작성한 답변으로 표시하지 않는다.
- 슬로건·네 카테고리·예시 답변 방식·제한 OFF·결제 OFF를 유지한다.

화면 검토 후 연결 개발 순서는 **사용자 인증·권한 분리 → 서버 저장 → AI 연결 → 실제 상담 알림**이다. 이번 수정에서 연결 작업은 시작하지 않았다.

## 1. 제품 정의

선물(선배에게 물어봐)은 세무사무소 신입 실무자가 사수에게 묻기 어려운 업무·응대·직장생활·커리어 고민을 편하게 물어보는 멘토 서비스다.

브랜드 문구는 **후배가 선배가 되는 날까지**다. 친근함은 닉네임을 부르는 말투와 구체적인 실무 도움으로 만들며, 과한 캐릭터 세계관이나 게임 장치를 추가하지 않는다.

사용자의 최신 결정이 이전 기획보다 우선한다. 제공 횟수·카테고리 한도·유료 전환 시점은 미정이며, 이번 MVP에서 제한과 결제는 모두 OFF다. ‘그냥 고민 좀 들어줘’는 향후에도 기본 무료 영역으로 유지하려는 방향이다. 과거에 제안된 하루 3회·주 1회 등의 수치를 확정값으로 구현하지 않는다.

## 2. 시제품과 실제 연결의 구분

현재 `index.html`은 준비된 분기형 예시 답변과 브라우저 로컬 저장을 사용한다. AI 모델, 인증, 서버 DB, 실제 선배, 외부 알림은 연결되지 않았다. 시연 화면을 실제 서비스처럼 표시하지 않는다.

연결 개발에서 ‘완료’는 버튼이 보이는 상태가 아니라, 실제 권한·저장·실패 처리·전송 결과까지 확인된 상태를 말한다.

## 3. 변경하지 않을 화면 기준

### 홈

사용자가 선배 자리로 조심스럽게 찾아왔을 때 먼저 말을 건네는 느낌으로 만든다.

- “엠버, 오늘은 어떤 게 어려워?”
- “엠버, 무슨 고민 있어?”
- “엠버, 뭐 하나 물어보려고?”
- “엠버, 오늘 헷갈린 게 있었어?”
- “엠버, 잠깐 이야기할까?”
- “엠버, 어떤 얘기부터 해볼까?”

한 번 들어왔을 때는 같은 문구를 유지한다. 홈으로 다시 들어오거나 새로 접속하면 직전 문구와 겹치지 않게 바꾼다. 입력 중 자동으로 바꾸지 않는다. 카메라나 감정 분석을 사용하지 않는 상태에서 “표정이 안 좋네”처럼 관찰한 척하지 않는다.

카테고리 명칭은 아래 네 개로 유지한다.

1. 실무가 헷갈려
2. 거래처 때문에 난감해
3. 사수한테 묻기 애매해
4. 그냥 고민 좀 들어줘

### 닉네임 카드

닉네임과 경력 옆에 작은 새싹·나무 그림만 넣는다. 앱 전체에 나무 컨셉을 확장하지 않는다. 성장단계명·물주기·햇빛·영양분·분야별 화분·숲·게임 보상은 추가하지 않는다.

### 채팅

AI라는 점을 분명히 표시하되, 말투는 설명 잘해주는 선배처럼 편하게 한다. 답변은 필요한 확인 질문 1~2개와 다음 행동 중심으로 짧게 쓴다. 모든 답변에 동일한 다섯 개 제목을 반복하지 않는다.

실제 선배 답변은 이름·검증된 경력 정보·답변 시간을 별도 표시한다. AI가 제니 본인인 것처럼 말하거나 제니가 아직 쓰지 않은 답변을 작성한 것으로 표시하지 않는다.

### 성장기록

질문을 모아서 다시 확인할 수 있게 하고, 사용자 스스로 남긴 배운 점과 선배가 실제로 남긴 피드백을 함께 보여준다.

질문 횟수·주제 수는 사용 기록일 뿐이다. 질문이 복잡해졌다는 이유만으로 정확한 판단을 했거나 업무를 능숙하게 수행했다고 판정하지 않는다. 반복 질문도 불이익으로 삼지 않는다.

후속 버전에서 질문 방식의 변화를 요약한다면 반드시 근거 메시지와 날짜를 연결한다. ‘관찰 가능한 표현의 변화’와 ‘직접 수행한 결과’를 구분하고, 근거가 없으면 평가하지 않는다. 사용자는 기록을 수정·삭제할 수 있어야 한다.

## 4. 사용자 식별과 권한

닉네임은 호칭이지 인증수단이 아니다. 같은 닉네임을 쓰는 사용자를 같은 사람으로 처리하지 않는다.

정식 버전은 안정적인 사용자 ID와 인증을 사용한다. 다른 기기에서도 기록을 불러오려면 동일 계정임을 확인해야 한다. 체험 모드를 제공하면 체험 기록과 실제 계정 기록을 구분하고, 계정에 옮길 때 사용자에게 확인한다.

권한은 일반 사용자·멘토·운영자로 나눈다. 닉네임 변경이나 화면 URL 입력으로 멘토·운영자 권한이 생겨서는 안 된다. 클라이언트에서 버튼을 숨기는 것만으로 접근을 제한하지 않는다.

일반 사용자는 자신의 대화·기록만 읽고 수정한다. 멘토는 본인에게 배정된 상담과 사용자가 그 상담에 공유한 메시지만 본다. 사용자 전체 이력과 고민상담을 기본 공개하지 않는다. 운영자가 예외적으로 접근하는 경우 역할·사유·열람 로그를 설계한다.

## 5. 데이터 구조 제안

`id`, `conversation_id`, `role`, `content`, `created_at`, `request_id`, `status`, `source_type`, `knowledge_references`, `risk_flags`

한 대화 안에 여러 사용자·AI 메시지가 오가도록 분리한다. 재시도 때문에 같은 메시지가 두 번 생성되지 않도록 요청 ID를 사용한다. 실패한 AI 요청은 답변 완료로 표시하지 않는다.

`id`, `user_id`, `conversation_id`, `assigned_mentor_id`, `question_summary`, `profile_snapshot`, `status`, `created_at`, `answered_at`, `closed_at`

### mentor_messages

### notifications

`id`, `recipient_id`, `type`, `entity_id`, `channel`, `status`, `idempotency_key`, `attempt_count`, `created_at`, `sent_at`, `read_at`

### knowledge_cards

`id`, `category`, `situation`, `question_examples`, `clarifying_questions`, `applicability`, `workflow`, `client_script`, `senior_script`, `encouragement_basis`, `warnings`, `source`, `author_id`, `reviewer_id`, `reviewed_at`, `valid_from`, `valid_until`, `reuse_consent_id`, `status`, `version`

`status`는 `draft → in_review → approved → archived`를 기본으로 한다. `approved`라고 해도 적용 조건·기준일이 맞는지 확인한 후 검색에 사용한다. 출처가 없는 경험을 ‘제니의 노하우’로 표시하지 않는다.

### usage_events / service_policies

사용량 집계와 운영 정책을 분리한다. 일반 질문·고민상담·실제 선배 상담의 정의와 차감 단위는 추후 확정한다. 플래그가 OFF인 현재는 숫자를 넣더라도 실제 제한을 적용하지 않는다. 기술 장애로 재전송한 요청은 중복 집계하지 않는다.

## 6. 실제 AI 응답 흐름

사용자 메시지 저장 → 질문 의도와 필요한 조건 파악 → 승인된 노하우 검색 → 적용 가능성과 근거 확인 → 필요한 경우 먼저 질문 → 짧은 멘토 답변 또는 실제 선배 상담 제안.

숫자 하나의 ‘자신감 점수’만으로 법률·세무 질문을 통과시키지 않는다. 자료 부재, 조건 부족, 출처 간 충돌, 검토 시점 불명, 고위험 판단을 별도 사유로 관리한다.

세율·한도·법령·신고기한처럼 시점 의존적인 정보는 확인된 최신 근거가 있을 때만 말한다. 최신 근거 확인이 안 되면 구체적인 세액·가산세·적법성 결론을 만들어내지 않는다. 짧고 친근하게 말하는 것과 사실 확인을 생략하는 것은 다르다.

API 키와 멘토 권한 키는 브라우저에 넣지 않는다. 모델 호출은 인증된 서버 측에서 수행하고, 사용자 내용·검색한 문서는 신뢰할 수 없는 입력으로 취급한다. 그 안의 지시문을 시스템 명령으로 실행하지 않는다.

## 7. 100문100답 전환

현재 시제품에는 연결하지 않았다. 다음 작업에서 원본을 실제로 읽고, 질문별로 원문·출처·적용 조건·기준일·검토 상태를 보존한다. 제니의 경험과 검증이 필요한 법률·세무 사실을 분리한다.

원본이 있다는 이유만으로 내용을 모두 정답으로 취급하지 않는다. 확인되지 않은 항목은 자동 답변에서 제외하고, 확인 질문·자료 준비·사수에게 말하는 방법 같은 제한된 도움만 제공한다.

상담 답변의 저장은 모델 자체 재학습이 아니다. 승인된 노하우를 검색해 참고하도록 연결하는 것과 모델 학습을 구분한다.

## 8. 실제 선배 상담과 알림

1. AI가 답할 근거가 부족하거나 사용자가 사람의 경험을 원하면 상담을 제안한다.
2. 사용자가 공유할 요약·프로필·메시지를 확인하고 동의한다.
3. 서버가 상담 요청을 저장하고 접수 결과를 반환한다.
4. 저장 성공 후 운영자 알림 작업을 생성한다.
5. 멘토가 답변을 저장하면 사용자 알림 작업을 생성한다.
6. 사용자가 답변을 열면 읽음 상태를 기록한다.

접수 저장과 알림 발송은 서로 다른 상태다. 상담이 저장돼도 알림 발송은 실패할 수 있으므로 각각 표시하고 재시도한다. 재시도 시 상담이나 알림이 중복 생성되지 않도록 한다.

외부 알림에는 민감한 질문 전문을 넣지 않는다. ‘새 상담이 접수되었습니다’ 또는 ‘선배 답변이 도착했습니다’와 로그인 후 열 수 있는 링크를 기본으로 한다. 상담 목적에 따라 필요한 범위의 내용만 표시하도록 설정한다.

멤버 개인의 실제 근무 상태나 답변 시간이 확인되지 않으면 ‘지금 회사에 있어’ ‘오늘 퇴근하면 답해줄게’를 확약하지 않는다. 사용자에게는 비동기 상담임을 안내하고, 긴급 업무를 기다리게 하지 않는다.

## 9. 예외 및 상태

- 저장 실패: 접수 완료로 표시하지 않고 입력을 보존한다.
- 답변 실패: 다시 보내기와 상담 전환을 제공한다.
- 대기 중 같은 상담 재요청: 기존 상담으로 안내한다.
- 멘토 부재: 운영 정책에 따른 대기 안내와 요청 취소를 제공한다.
- 사용자 대화 삭제: 상담에 공유한 사본·노하우 초안·보관 정책에 미치는 범위를 설명하고 처리한다.
- 알림 수신 거부: 앱 안에서 답변 상태는 확인할 수 있게 한다.
- AI와 멘토가 다른 조언: 확정 답을 덮어쓰지 않고 차이와 추가 확인 필요성을 설명한다.
- 실제 위험이 큰 상황: 무조건 안심시키거나 ‘사수에게 안 들키면 된다’는 식으로 안내하지 않는다.

## 10. 통과 기준

- 닉네임은 자연스럽게 쓰고, 그 외 이름으로 사람을 잘못 식별하지 않는다.
- 그림은 닉네임 카드에만 존재한다.
- 홈 인사가 타이핑 중 바뀌지 않는다.
- AI·사람·시연 답변을 구분한다.
- 근거 없는 세법 결론·상담 전송 완료·외부 알림 완료·성장 평가가 나오지 않는다.
- 사용자가 선택한 범위만 상담에 공유된다.
- 다른 사용자의 ID를 요청해도 대화가 노출되지 않는다.
- 멘토는 배정된 상담 외의 대화를 볼 수 없다.
- 사용량 제한·결제는 계속 OFF다.
- 저장·모델·알림 장애 시 입력과 상태가 일관되게 유지된다.
- 삭제·동의 철회·백업·복구 흐름을 실제 서버 환경에서 별도로 시험한다.
